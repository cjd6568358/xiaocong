# 04 · 路线可行性评估与建议

> 目标：让这个插座重新可用。厂商已倒闭，云端已停服。

---

## 决策树（先做这个判断）

```
插座固件里烧死的云端地址是什么？
├─ 是域名（如 gw.ixiaocong.com）
│    └─ ✅ 局域网 DNS 劫持可行 → 自建服务端（路线 A）
├─ 是硬编码 IP
│    └─ ⚠️ 需要透明代理 / iptables 重定向 → 自建服务端（路线 A'，较麻烦）
└─ 无法确定 / 固件可刷
     └─ ✅ 直接刷开源固件（路线 B，推荐）
```

**这个判断只需要一次抓包**，是整件事的岔路口。

---

## 路线 A：自建服务端

### 可行性：协议层面完全可行

控制协议是明文 JSON + 标准 MQTT，没有任何私有加密。

### 需要实现的东西

| 组件 | 工作量 | 说明 |
|---|---|---|
| MQTT broker | ★☆☆ | mosquitto / EMQX，开 TLS |
| TLS 证书 | ★☆☆ | 用自己的证书即可 —— 配网时通过 `crt` 参数下发给设备 |
| HTTP API 桩 | ★★★ | 约 15 个核心端点 |
| 签名校验 | ★★☆ | MD5 算法已还原（[01](01-HTTP-API与签名.md)） |
| 服务端订阅绑定 | ★★☆ | 复刻 `device/subscribe/all` 语义 |

最小可用端点集（让一个已配网设备能被控制）：

```
client/config          ← 返回你的 broker 地址、clientId、clientKey
user/login             ← 发 token
device/subscribe/all   ← 给客户端绑定订阅
device/list / index    ← 设备列表
parameter/list         ← 设备参数
device/bind
device/getBindInfo
device/getDiscovered
```

### 硬前提

**插座固件必须被指向你的服务器。** 而固件里烧死的地址未知：

- 若为**域名** → 局域网内跑 DNS 服务器 + DHCP 下发，把域名解析到你的服务器。**可行**。
- 若为**硬编码 IP** → 需路由器 iptables / 透明代理劫持。较麻烦但可行。
- 若固件**校验证书**（类似 App 那样 pin）→ 难度大增。
  不过 `crt` 是随配网下发的，理论上设备会信任它（见 [03 §5.6](03-配网与native.md)）。

### 首次配网

- 首选：改 `DeviceAddSoftApActivity:164` 的 `domain`/`crt`，
  或用 [03 §9](03-配网与native.md) 自写配网客户端 → 见 [05-免拆机方案.md](05-免拆机方案.md)
- 保底：Android 10 以下仍可运行原 App → 用旧手机 / 模拟器配一次网，之后永不再需要配网
- 或直接 JNI 复用厂商 `libsoftAp.so`

### 结论

协议层完全可行。当初写的"只剩一个真前提：固件是否遵守 `domain`/`crt`"，
**现在已经有答案了 —— 两个都不遵守**（2026-10-02 真机）：

| 前提 | 真机结论 |
|---|---|
| 固件遵守 `crt`？ | ❌ 不遵守。`crt` 非空 → 设备**整包拒绝**（重发 `ch_pubk`），连 WiFi 配置都不应用 |
| 固件遵守 `domain`？ | ❌ 不遵守。给了**公网 IP** 仍去查内置的 `iot.ixiaocong.com` |

⇒ 本路线（"让设备主动指向我们的服务器"）**走死**。
但注意：**这不是"免拆机"走死了** —— 换一条路就行：
**劫持固件内置域名**（伪造 DNS 应答，把 `iot.ixiaocong.com` 指到自己），
固件不校验证书，TLS 直接握手通过。这条路已完全跑通并搬到光猫常驻，
见 [05-免拆机方案.md §11 / §12](05-免拆机方案.md)。

教训：**"报文里带了某参数" 不等于 "固件会采用它"**。报文侧已证实的结论，
在固件侧真机验证之前只能是假设。

## 路线 B：刷开源固件 ✅ 推荐

### 优势

- **完全摆脱云端**：本地控制、局域网、无需任何厂商服务器
- **协议开放**：ESPHome / Tasmota / ESPurna 都支持 MQTT + Web UI
- **可接入 Home Assistant**，长期可控
- 仓库里已有半成品：`wukongcong.ino` 就是这个思路（修复版见 `firmware/`）

### 硬件

PDF 确认是 **ESP8266** 方案。`wukongcong.ino` 透露的引脚定义：

| 功能 | GPIO |
|---|---|
| 继电器输出 | 14 |
| 指示灯 | 4 |
| 按键 | 13 |

### 成本

| 项 | 说明 |
|---|---|
| USB-TTL 串口 | 几块钱 |
| 拆机 + 接线 | 需要焊接或用探针（免焊接线） |
| 刷机 | esptool / Tasmota Web Installer |

### 能刷什么

| 固件 | 特点 |
|---|---|
| **ESPHome** | 与 Home Assistant 深度集成，YAML 配置，推荐 |
| **Tasmota** | 成熟，Web UI + MQTT + 定时，无需服务器也能用 |
| **ESPurna** | 轻量 |
| 自己写 | 仓库里的 `wukongcong.ino`（Blinker） |

### 风险

- **需要拆机**（可能破坏外壳）
- **引脚定义需实测确认**（`.ino` 里的定义可能不适用于你的具体批次）
- **不可逆**：刷了就回不去原厂（但原厂已死，无损失）
- 建议**先备份原固件**（esptool `read_flash`），万一要回滚

### 结论

**风险最低、收益最高、与云端死活无关。** 强烈推荐作为主攻方向。

## 一句话总结

> **协议已全部破解（含 native 加密），不构成障碍。**
> 曾经的岔路口是**固件行为**：改 `domain`/`crt` 后它是否照做。
> **2026-10-02 真机已给答案：两个都不照做** ⇒ 改为**劫持固件内置域名**（路径 E），
> 已完全跑通并常驻光猫，**免拆机目标达成**。
> 刷开源固件不再是必需，退回保底位置。
