## 1. 关键发现：配网时设备接受自定义云端地址

### 证据链

配网 native 函数签名：

```java
startSoftAp(
    String broadAddress,   // "192.168.4.255"
    String ssid,           // 家里 WiFi SSID
    String password,       // 家里 WiFi 密码
    String domain,         // ★ 云端域名
    String crt,            // ★ 云端 CA 证书
    String clientId,
    String checkCode)
```

- `domain`/`crt` 会被 `strcpy` 到全局变量，并由 `app_step1` 编进 `ch_data` 报文
  （AES-128-CBC + base64）—— **确实一路传到了设备**。
- 原厂 App 传的是**空串**（`DeviceAddSoftApActivity.java:164`，`Constants.MAIN_VERSION_TAG = ""`）。
- 两个 `.so` 里搜不到任何域名 → 排除"so 内置默认域名"。

### 推论

```
domain="" + crt=""        →  使用固件内置的默认云端
domain="xxx" / crt="yyy"  →  使用指定的云端   ← 白牌 / 私有部署用法
```

标准白牌设计：厂商给不同客户定制私有云时，配网下发不同域名 + 证书；
消费版 App 留空 = 用出厂默认。

> 🎯 如果设备确实遵守 `domain`/`crt`，只要在配网时填入**自己的域名和证书**，
> 设备就会连到**我们自己的服务器** —— 全程不拆机。
> 支点就是 [`server/`](../server/) 里那套自建服务端。

完整 native 细节见 [03-配网与native.md](03-配网与native.md)。

## 4. 备选：局域网直控（也免拆机）

`libxcsdk.so` 里有完整的 CoAP 局域网通道：

```
CoAP over UDP 255.255.255.255:13078
  GET Uri-Path="Scan"    payload {"scanType":N,"productId":"..."}   发现设备
  GET Uri-Path="Getkey"  payload {"Query":"1"}                      取局域网密钥 ★
  cmdExec opcode 4 = CMD_Snapshot / 5 = CMD_Control
```

⚠️ **但这条通道在 App 里只在 `xconfig` 配网流程中被使用**
（`XcSdkManager.startConfig` → `DeviceSdk.cmdExec(2, ...)` 发现设备）；
**稳态控制 App 仍只走云端 MQTT**。

### ❌ 真机实测：此路不通

插座配网成功后位于 `192.168.1.23`，对它的实测结果：

| 探测 | 工具 | 结果 |
|---|---|---|
| 25 个常见 TCP 端口 | `tools/tcp-scan.js` | **全部关闭** |
| CoAP `Scan`（6 种 payload × 广播/子网广播/单播） | `tools/coap-probe.js` | **零响应** |
| ICMP | `ping` | 通（TTL=255），设备确实在线 |

→ 固件在未绑定状态下**不监听任何局域网控制端口**，也没有可探测的服务。
   本方案排除（除非先改固件）。

## 5. 备选：OTA 刷固件（为什么不是首选）

App 确实有固件升级接口（`device/sdk/upgrade`），且**免拆机**。但有一个硬障碍：

> **没有可刷的固件镜像。**

- 刷开源固件需要 **ESP8266 完整镜像**，而这个设备的 OTA 协议、bootloader 是否校验签名、
  分区表如何 —— 全都未知
- 要拿原厂镜像往往还是得先有设备访问权限（OTA dump 或读 flash）
- 若 bootloader 校验签名 → **没有厂商私钥就刷不进任何自制固件**

所以 OTA 适合作为**第二阶段**：先用路线 A 控制住设备，再考虑通过自建服务器推送固件。

## 9. 路径 E/F 的工具：二层旁路采集（`tools/lan-mitm.py`）

### 9.1 为什么必须 ARP 欺骗

Wi-Fi 下**看不到别的终端的单播流量**（AP 只把帧转发给目标站点），实测确认：
网卡能抓到本机 + 网关的流量，以及**其他设备发出的广播帧（ARP）**，但抓不到
其他设备的单播。

但插座要访问的一切**都在子网外**：

| 插座的目标 | 走法 |
|---|---|
| DNS `192.168.1.1` | 子网内 → 但它是网关 |
| DNS `223.5.5.5` | 子网外 → 经网关 |
| 云端服务器（公网 IP） | 子网外 → 经网关 |

所以**只要骗插座"网关 MAC 是我"**，它出子网的全部流量就都会送到我们网卡上 ——
DNS 查询、TCP 连接、TLS ClientHello 一个不落。

### 9.2 关键前提：不需要管理员权限

实测本机（普通用户）环境下：

| 能力 | 结果 |
|---|---|
| Npcap 打开网卡抓包 | ✅ **可以**（`wpcap.dll` 在 System32） |
| scapy `sendp` 注入原始帧 | ✅ **可以** |
| `net session`（管理员命令） | ❌ 拒绝访问（确认非管理员） |

也就是说 **抓包 + 发包都不需要管理员**，ARP 欺骗可以在普通用户下完成。
（`pktmon` 需要管理员，故此前判定"本机无法抓包"是错的。）

### 9.3 三种模式

```powershell
# 纯观察：不改插座配置，只采集（插座照常连官方云端）
python tools/lan-mitm.py --mode watch --seconds 300

# ARP 欺骗 + 采集：截获插座发往子网外的一切
python tools/lan-mitm.py --mode spoof --target 192.168.1.23 --seconds 600

# ARP 欺骗 + 只截 DNS 并伪造应答，把插座引到自建服务器
python tools/lan-mitm.py --mode dns --target 192.168.1.23 --fake-ip 192.168.1.20

# 收工恢复（发正确的 ARP）
python tools/lan-mitm.py --restore
```

采集结果：`lan-capture.log`（可读日志）+ `lan-samples.jsonl`（结构化样本，
含 `dns_query` / `tls_clienthello` / `tcp_syn` / `arp_*` / `dhcp` 等类型）。

### 9.4 一键跑完（配网用出厂默认 + 采集）

### 9.7 路径 E 的下一步：`--mode dns`（伪造应答）

既然插座**硬编码用 `223.5.5.5`**，在路由器上加静态 DNS **没用**，
只能在链路上伪造应答。做法（工具已就绪）：

```powershell
# 持续伪造：让 iot.ixiaocong.com 解析到自建服务器
python tools/lan-mitm.py --mode dns --fake-ip 192.168.1.20 --seconds 600

# 同时开多端口监听网，看它连哪个端口、TLS 能不能过
PORTS=443,8883,1883,8888,8443,9999,... node tools/port-watch.js
```

预期能看到：
1. 插座**立刻**（11 秒内）向 `192.168.1.20:<端口>` 发起 TCP —— **端口本身是重要情报**
2. TLS ClientHello 的 **SNI**（应为 `iot.ixiaocong.com`，可交叉验证）
3. **TLS 握手能否完成** ← 最关键：
   - 若握手成功 → 固件**不校验证书** → 直接接管，全程免拆机 ✅
   - 若握手失败/拒绝 → 固件用内置 CA 校验 → 仍需解决 `crt`（回到路径 A）

> 因为插座每 ~11s 就重试一次，这个实验**不需要重新进配网模式**，
> 插座只要在线就能测。但注意它约 5 分钟会放弃重试并离线，
> 所以要么在它上线后立刻跑，要么让伪造持续挂着等它回来。

### 9.8 ★ 路径 E 最终结论：已完全跑通（2026-10-02）

§9.7 的三个"预期"全部拿到了实测答案，而且是最好的那种：

| 问题 | 实测答案 |
|---|---|
| 插座连哪个端口？ | **8188**（固件硬编码，不是 443） |
| TLS 握手能过吗？ | ✅ **能** —— 固件**不校验证书**（自签证书即可） |
| 能接管到哪一步？ | ✅ **能收能发** —— 收到 `snapshot`，下发 `control` 真实开关继电器 |

关键证据：`tools/fake-cloud.py` 在 TLS 通道里 `PUBLISH topic=control {"command":{"switch":1}}`，
**插座继电器当场响**（01:07:30 开、01:08:50 关，可复现）。设备还会把 `messageId` 原样回显，

> ⇒ **路径 E 不需要 `crt`、不需要改插座任何配置，已经是一条完整的可执行路线。**

## 10. 落地部署：服务端放哪？放光猫行不行？

> 用户原话：「我本来就打算把服务端放在光猫上，光猫上有 dns 服务器吗？能改吗？」

**先回答三个具体问题：**

1. **光猫上有 DNS 服务器吗？** —— 有。`192.168.1.1:53/UDP` 是开的，
   `nslookup 任意域名 192.168.1.1` 能解析（它是个转发器）。Web 管理页在 80 端口（`.gch` 页面，gb2312）。
2. **能改吗？** —— 能改，**但改了也白改**（见约束 1）。
3. **所以服务端能放光猫上吗？** —— **能。** ⚠️ 本文档早先写的"不能"是**错的**，
   混淆了"光猫不能当服务器"和"不能把 DNS 应答写成光猫自己的地址"。详见下面「关键澄清」。

**两条硬约束（都是实测，不是推测）——注意它们的"真正含义"：**

| # | 约束 | 出处 | **真正含义** |
|---|---|---|---|
| 1 | 固件**硬编码 DNS = `223.5.5.5`**（AliDNS），**完全不理会** DHCP 下发的 `192.168.1.1` | [03 §5.9](03-配网与native.md)（66/66 次采样） | 光猫**自己**的 DNS 设置对插座无效（它不问光猫）。⇒ 必须**主动劫持**：把插座发往 `223.5.5.5:53` 的包 REDIRECT 到本地 |
| 2 | 固件**拒绝私有网段 IP**（防 DNS 重绑定）：应答给 `192.168.1.x` 时插座只 ARP 不 SYN；换成公网 `203.0.113.9` 才立刻连 | [07 §1.2](07-真机云端协议.md) | **只是说不能把 DNS 应答写成 `192.168.1.1`**。解法：应答一个**公网地址**，再用一条 DNAT 把它转回内网（hairpin NAT）。**这不构成"光猫不能当服务器"的障碍** |

### ★ 关键澄清：光猫是网关，它天生就在路径上 —— 比 PC 更有优势

我的 PC 能劫持，靠的是**ARP 欺骗抢网关 MAC**；**光猫不用抢，它就是网关**。
插座发给 `223.5.5.5` 的 DNS、发给 `203.0.113.9` 的 TCP，**本来就都先到光猫**。
所以光猫上只要两条规则就成立：

```sh
# 1) 截下插座发往 223.5.5.5 的 DNS（插座硬编码，只能这样截）
iptables -t nat -A PREROUTING -i br-lan -p udp --dport 53 -j REDIRECT --to-ports 53
#    ↑ 再让本地 dnsmasq 回一条：address=/iot.ixiaocong.com/203.0.113.9

# 2) 让"公网地址"回头落到真正跑服务的机器（hairpin NAT）
iptables -t nat -A PREROUTING -i br-lan -d 203.0.113.9 -p tcp --dport 8188 \
         -j DNAT --to-destination 192.168.1.20:8188
```

插座看到的是"公网地址 203.0.113.9"（过防重绑定），实际落到内网服务上。
**不需要 ARP 欺骗，也不需要在 PC 上常驻抓包。**

### ★ 实测：你这台光猫本身就能跑程序

探了一下 `192.168.1.1`：

| 端口 | 状态 | 说明 |
|---|---|---|
| 23/tcp | **OPEN** | telnet，banner 直接回 `F4610U` → 设备是**中兴 ZTE F4610U** |
| 80/tcp | OPEN | Web 管理页（`.gch`，gb2312，运营商定制） |

F4610U 是**跑 Linux（BusyBox）的 ONT**，社区（恩山论坛、开源工具 zteOnu 等）有成熟方法拿 root shell。
⇒ **"光猫能不能跑程序"的答案是：能。**

但真要**把服务端跑在光猫上**，还有三件现实问题：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **没有 Python / scapy** | 现有 `tools/fake-cloud.py` 依赖 scapy 做用户态 TCP。若改用上面的 DNAT，内核会正常处理 TCP，就**不再需要 scapy** —— 只需一个普通 TCP+TLS+MQTT 服务端。但得重写成**静态二进制**（Go/C，自带 TLS1.0/1.1 支持）才能塞进光猫 |
| 2 | **flash 小 + 重启可能被恢复** | 光猫可写分区通常只有几 MB，且 TR-069 远程管理可能把改动刷回去 → **持久化难** |
| 3 | **风险** | 改坏会断网；运营商可能远程重置或上门换机 |

### 落地形态对比（修正版）

| 方案 | 要常开 PC | 要改什么 | 干净度 | 备注 |
|---|---|---|---|---|
| **① 局域网常开小机跑 ARP 劫持** | 要 | 不用 | ★★☆ | 就是现在这套，**已验证可用**；ARP 欺骗要常驻，且顺带劫持插座全部出网流量 |
| **② 光猫只做劫持，服务端放内网** ★推荐 | 要（NAS/树莓派等常开小机） | 光猫加 2 条 iptables | ★★★★ | **不在光猫上跑自定义程序**，规避 flash/持久化风险；只借它的 NAT 能力 |
| **③ 服务端直接跑在光猫上** | 不用 | 光猫拿 root + 塞静态二进制 | ★★★ | 最省一台机器，但要重写程序 + 解决持久化 + 承担断网风险 |
| **④ 换/刷 OpenWrt 路由器** | 不用 | 换设备 | ★★★★★ | 前提是你家能用自备路由器（很多光猫可改桥接） |
| **⑤ 公网 VPS** | 不用 | 在链路上劫持 DNS | ★★★★ | `iot.ixiaocong.com` 已 NXDOMAIN；**理论上可注册它**，那样连劫持都不用 —— 但涉及原厂商商标，不建议 |
| **⑥ 直接刷 Tasmota/ESPHome** | 不用 | 拆机接线 | ★★★★★ | 见 [../firmware/README.md](../firmware/README.md) |

> 一句话：**"放光猫上"完全可行**，光猫是网关、天然在路径上，还省掉 ARP 欺骗。
> 真正要权衡的只是"程序跑在光猫里"（要 root + 重写 + 持久化）还是
> "光猫只做劫持、程序跑在内网小机"（改动最小、最稳）。

## 12. ★★★★★ 落地实现：`ixc-go` 常驻光猫（2026-10-02 完成）

> 这一节是**最终交付形态**。§10 里关于"光猫上没有 iptables""要 hairpin DNAT"的说法
> 都是**当时的推测**，实际摸完设备后**已修正**，以本节为准。
>
> 程序原名 `ixc-ont`，2026-10-02 改名为 **`ixc-go-arm64_upx`** 并搬到 `/f4610u/app/`
> （沿光猫 `/f4610u/bin` 的 `*_upx` 命名习惯），**UPX 压缩后 1.52 MB**。
> 回环规则从程序里挪到 `/f4610u/user_init.sh` 常驻（理由见 §12.2②）。

### 12.1 光猫真实底细（全部实测）

| 项目 | 实测结果 | 影响 |
|---|---|---|
| 机型 / 系统 | 中兴 **ZTE F4610U**，`ZX279131`(Cortex-A53×2, 512MB)，**OpenWrt 19.07.7**，内核 **4.1.25 aarch64** | 能跑静态 arm64 二进制 |
| **netfilter** | **活的**：`/proc/net/ip_tables_names` = `nat mangle filter` | 能加规则 |
| **iptables 命令** | **有**，只是不在 PATH：`LD_LIBRARY_PATH=/f4610u/lib /f4610u/bin/iptables_upx` → **v1.4.13** | ⚠️ 之前记的"没有 iptables"是错的 |
| 可用 target | `REDIRECT DNAT SNAT MASQUERADE NFQUEUE MARK TCPMSS LOG` + ZTE 定制 `URLREDIRECT URLACCEPT MAC_DNAT` | 够用 |
| 可用 match | `mac` ✅、`multiport`、`mark`、`conntrack`、`state`…；**`addrtype` 没有** ❌ | 能按 MAC 精确匹配；不能按 `--dst-type LOCAL` 匹配 |
| `:53/UDP` | **已被光猫自带解析器占用**（`0.0.0.0:53`） | 自己的 DNS 应答器只能另起端口 + REDIRECT |
| LAN 侧 | `br0 = 192.168.1.1/24`；2.4G SSID = **`PDCN_IOT`**(BSSID `30:1f:48:c3:f7:a3`) | 插座和 PC 同二层 |
| WAN | `ppp0` = **`139.227.20.142`**（公网，PPPoE） | 就是 DDNS 解析值 |
| 开机自启 | `/etc/rc.local` 里已有 **`/bin/sh /f4610u/user_init.sh &`** | 现成的用户钩子，不必碰系统文件 |
| 其它 | 用户已在跑 `easytier-core` / OpenList；`crond` 在跑，crontab 每 5 分钟更新 `allin.dns.army`（dynv6） | —— |

### 12.2 三条关键实测结论（决定了方案长什么样）

**① 局域网访问光猫自己的 WAN IP —— 完全不回环。**

从 PC 打 `139.227.20.142` 的 **80 / 10022 / 11010 / 15888 / 18999 / 8188 全部超时**，
而打 `192.168.1.1` 同样端口全通。conntrack 里也**没有任何** WAN IP 的流记录
⇒ 包既没被本地投递、也没被转发，是**在 netfilter 之前就被吃掉了**（ZTE 转发引擎）。
**所以"用 DDNS 域名直连光猫"这件事，光靠 DNS 解析是不够的，必须补一条 iptables 规则。**

**② 补一条 REDIRECT 就修好了。最终采用的写法（★ 关键改进）。**

最初写的是把当前 WAN IP 写死：

```sh
# ⚠️ 能用，但【不要用】—— 见下面的理由
export LD_LIBRARY_PATH=/f4610u/lib
$IPT -t nat -I PREROUTING 1 -i br0 -d 139.227.20.142 -p tcp --dport 8188 \
     -j REDIRECT --to-ports 8188
```

**毛病**：PPPoE 重播会换 WAN IP，规则随之失效。而且失效时**规则还在表里**，
只是不再匹配任何包 —— 现象是"插座静默失联"，排查起来极痛苦。

**最终写法：用「目标不是内网段」等价表达，永不失效。**

```sh
export LD_LIBRARY_PATH=/f4610u/lib
IPT=/f4610u/bin/iptables_upx
$IPT -t nat -D PREROUTING -i br0 ! -d 192.168.1.0/24 -p tcp --dport 8188 \
     -j REDIRECT --to-ports 8188 2>/dev/null          # 幂等：先删同规格旧规则
$IPT -t nat -I PREROUTING 1 -i br0 ! -d 192.168.1.0/24 -p tcp --dport 8188 \
     -j REDIRECT --to-ports 8188                      # 再插到最前面
```

这台光猫的 iptables 1.4.13 **没有 `addrtype`**，写不了"目标是本机地址"，
所以用"目标不是内网段"来等价表达。实测被接受（`iptables -L -v` 显示为
`!192.168.1.0/24`），`-C` 幂等检查也正常。

> 这条规则**常驻在 `/f4610u/user_init.sh` 里**，不由程序管理（程序里加 `-hairpin`
> 仍可改回自己铺）。理由是：它不依赖任何运行时参数、也不需要跟随 WAN IP，
> 放在开机脚本里最合适。
>
> ⚠️ **必须插在 `PREROUTING` 最前面**。ZTE 自己的 `srvcntrl` / `fwports` /
> `portmapp` 等几条链排在后面，它们会先把包处理掉，规则排后面等于没写。

加完后，从 PC 连 `139.227.20.142:8188` → **TLS 1.1 握手成功**，光猫端日志有记录。
`DNAT --to-destination 192.168.1.1:8188` 与 `REDIRECT` **等效可用**。
⇒ **`allin.dns.army` 可以直接用**（配合这条规则）。

**③ 也可以完全不用 iptables —— 给 br0 挂一个"公网 IP"别名。**

```sh
ifconfig br0:0 203.0.113.9 netmask 255.255.255.255 up
```

`203.0.113.9` 属于公网段（TEST-NET-3），**能过固件的防重绑定检查**；
挂在 `br0` 上之后，包从 `br0` 进来、目的地址就在 `br0` ⇒ **天然本地投递**，
不需要任何 nat 规则。已实测：TCP 通 + TLS 握手成功。

> 两种打法各有取舍：
> **别名法**不依赖 WAN IP（PPPoE 重播换 IP 也不受影响），但要动接口；
> **WAN IP 重定向法**不动接口，但规则里的 IP 会随 PPPoE 变化，需要刷新。
> 最终实现**两个都上，互为兜底**：
> ② 那条 `! -d 192.168.1.0/24` 规则负责主路径，`br0:0` 别名留着兜底

- **不按 MAC 劫持**。改为劫持"光猫自己发往 DNS 上游的查询"，因此

#### 12.3.1 ★ 为什么 PREROUTING 按 MAC 那条实测无效

**现象**：ixc-go 04:25 重启后 9 小时零连接，`-i br0 -m mac <插座MAC> -p udp --dport 53`
的 REDIRECT 规则**计数始终为 0**，而插座明明在线、也在发 DNS。

**根因**：**nat 表只对「新建连接」的首包遍历规则**。已经 confirm 的 conntrack 流，
后续包直接走内核里存好的转换表，**根本不查 nat 规则**。插座那两条 DNS 流
（`→223.5.5.5` 和 `→192.168.1.1`，**源端口恒为 49153**）在很早之前就建好了，
每 ~2 秒刷新一次，UDP conntrack 超时 300 秒 ⇒ **永不超时** ⇒ 永远等不到"新流"。

**关键证据**：
- filter 表是**逐包遍历**的：60 秒里 INPUT 命中 19 次、FORWARD 12 次，
  dmesg 清楚打印 `IN=br0 PHYSIN=wlan0 SRC=192.168.1.11 DPT=53` ⇒ 包确实过 CPU
- 不带 `-i` 的全量 nat 规则 90 秒 114 命中，全是**别人的新流**，插座一个都没有
- 不是硬件快转：PC 对照实验里已建流照样被劫持

**绕法**：瓶颈不在插座那条流，而在光猫自己的转发链路上。
`/sbin/proxy` 每次向上游查询都是新流，所以 **nat OUTPUT 必然命中**。
⇒ 不用重启光猫、不用拔插座、不写死 MAC。

**排障时踩的坑**（写在这免得再犯）：
- **计数探针不能用 `-j ACCEPT`**（终止型 target，会把排在后面的规则饿死）。
  我一次插了 4 条 ACCEPT 探针，最宽泛那条在最前面，导致误判"`-i br0` 无效"。
  计数探针一律用 `-j LOG`（非终止）。
- `-i br0` 是对的。ARP 表的 Device 列写 `br0` 不代表入接口，要看 dmesg 的 `PHYSIN=`。

**★ 为什么正式版在 `/f4610u/app` 而不是 `/f4610u/bin`（2026-10-02 改）**

最早放在 `/f4610u/bin`（跟着 `*_upx` 命名习惯走）。后来按约定改成：
**调试用的一律 `/tmp`，正式的一律 `/f4610u/app`**。理由是
`/f4610u/bin` 是光猫原厂 + 第三方工具的目录（`iptables_upx`、
`dropbear-aarch64-static_upx`、`scp-aarch64-static_upx`…），
**自己写的东西放 `/f4610u/app`**，跟机器上已有的 `blinker-go-arm64_upx`、
`server-go-arm64_upx` 一致，一眼能分出"哪些是我们后来加的"。
`deploy.py` 部署时会顺手 `rm -f /f4610u/bin/ixc-go-arm64_upx`，
避免新旧两个副本并存、排障时搞混"到底跑的是哪个"。

**日志为什么一律 `/tmp`**：根分区是 overlay，实测**只剩 8.5 MB（已用 89%）**；
`/tmp` 是 tmpfs（220 MB）。日志重启即丢，正好 —— 反正只用来排障。
（跟 easytier 一个待遇。）

**为什么必须 UPX**：同上，空间太紧。
Go 静态二进制原样 5.18 MB，UPX 后 1.52 MB（压到 29.4%），省下的 3.6 MB 很实在。

> ① 调试实例**不会**开机自启，光猫重启就没了；要常驻还是得跑一次不带 `--debug` 的正式部署。

> 残留空行，反复部署会让开机脚本每次胖两行，已修。

### 13.2 为什么能跑（4.1.25 内核 vs 5.15 头文件）

静态二进制**没有 interpreter 段**，aarch64 内核直接加载执行，绕开光猫上那套
armhf + glibc 2.26 的用户态容器。工具链头文件是 5.15 的、目标内核是 4.1.25，
但实测 105 条命令没有一条因此出问题——**用到的 syscall 全是老接口**。

### 13.3 musl 编译 busybox 的 6 个坑

| # | 现象 | 处理 |
|---|---|---|
| 1 | `findutils/grep.c`、`editors/vi.c`：`RE_TRANSLATE_TYPE` / `re_syntax_options` 未定义 | musl 没有 glibc 的 GNU regex 扩展 → 关 `CONFIG_EXTRA_COMPAT` |
| 2 | 同上 | 关 `CONFIG_FEATURE_VI_REGEX_SEARCH` |
| 3 | `networking/inetd.c`：`rpc/rpc.h: No such file` | 关 `CONFIG_FEATURE_INETD_RPC` |
| 4 | `devfsd.c` / `d6_dhcpc.c`：`-Werror=format-truncation`、`-Werror=deprecated-declarations` | GCC 11 更严 → `CONFIG_EXTRA_CFLAGS="-Wno-error"` |
| 5 | `generate_BUFSIZ.sh --post` 以 rc=1 退出 | musl `<sys/user.h>` 不定义 `PAGE_SIZE` → 关 `CONFIG_FEATURE_USE_BSS_TAIL` |
| 6 | 链接期 `libsanitizer.spec` 不存在 | 关 `CONFIG_DEBUG_SANITIZE` |

**另外两个纠正：**

- busybox **没有** `CONFIG_OPTIMIZE_FOR_SIZE` 这个符号。优化级别由
  `Makefile.flags` 按 `CONFIG_DEBUG` 二选一：`DEBUG=n → -Oz/-Os`，`DEBUG=y → -O0 -g`。
  所以要 **关 `CONFIG_DEBUG`**，并在编译前用 `make V=1` 断言实际级别。
- **绝对不要用 `make CFLAGS=...`**：那会把 busybox 自己的一整套编译开关冲掉。
  加选项用 `CONFIG_EXTRA_CFLAGS`，交叉前缀用 `CONFIG_CROSS_COMPILER_PREFIX`。

### 13.4 `defconfig` 之外显式打开的 20 个 applet

`defconfig` 只给 402 个。以下 20 个默认是 `n`，但对一台光猫/路由器确实有用，
脚本里显式打开（符号名从各 `.c` 的 `//config:config XXX` 块确认，不是猜的）：

```
闪存工具（MTD）★ 备份/写回固件分区要用
  NANDWRITE NANDDUMP FLASHCP FLASH_ERASEALL FLASH_LOCK FLASH_UNLOCK
其它
  BBCONFIG(打印编译配置，事后审计) AR INOTIFYD RFKILL NETCAT(经典别名)
  READAHEAD FBSET TUNE2FS MKFS_REISER LZOPCAT UNLZOP UNCOMPRESS NUKE MINIPS
```

> `CONFIG_DEVFSD` 没开：devfs 早在 2.6.32 就从内核里删了，开了也没用。

### 13.5 用法

```sh
# 编译（在 10.0.0.4 上，建议去 /tmp 里跑）
mkdir -p /tmp/bbbuild && cd /tmp/bbbuild
bash /media/disk/backup/script/build_busybox_static.sh

# 部署到光猫
scp busybox-full-aarch64 root@192.168.1.1:/tmp/busybox-full
chmod +x /tmp/busybox-full
/tmp/busybox-full --list | wc -l          # → 418

# 想按裸命令名用（不要覆盖 /bin/busybox！）
/tmp/busybox-full --install -s /tmp/bbin
export PATH=/tmp/bbin:$PATH
echo hi | sha256sum
```

> ⚠️ **不要把 `/bin/busybox` 换掉。** 光猫的 `procd`、`/f4610u/user_init.sh`
> 等一整套启动流程都依赖系统 busybox，换掉有变砖风险。要用就放 `/tmp` 或
> `/f4610u/app/` 下，通过绝对路径或 `PATH` 前缀调用。

### 13.6 过程中的两个测量教训

1. **不要用 `head` 去截构建脚本自己的输出。** 管道提前关闭会给脚本发 SIGPIPE，
   脚本当场死掉，看起来像构建失败（实际这次就是被这么误杀过一次）。
2. **用 SSH 库读远端输出时，别拿「远端已退出且当前无数据」当结束条件。**
   最后一块数据常常还在路上，会**静默截断**——表现为 `find ... | wc -l` 报 1、
   `tar tjf | grep` 只出一条。我因此误判过「busybox 源码树缺了所有子目录
   `Config.in`」，实际有 25 个。正确做法是**以 EOF 为准**，或让远端把结果写进
   文件再单独 `cat` 回来。
