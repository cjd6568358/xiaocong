## 1. 怎么拿到的（方法论，可复现）

### 1.1 三层递进

1. **被动观察**（不改任何东西）：ARP 欺骗网关 → 截获插座 DNS 查询
   → 发现它只查 `iot.ixiaocong.com`，且用**硬编码 DNS `223.5.5.5`**（从不用 DHCP 下发的）
2. **DNS 中继**：把真实应答原样还给它 → 得到 **NXDOMAIN**（域名已不存在）
   → 插座永远拿不到 IP、**永远不会发起 TCP** ⇒ 中继这条路是死的
3. **伪造应答**：把域名指向我们自己的机器 → 插座才会走到 TCP/TLS

### 1.2 ★ 关键坑：固件拒绝私有网段 IP

伪造应答指向 `192.168.1.20`（私有）时：
插座**解析成功、也 ARP 询问了 `192.168.1.20`**，但**死活不发 TCP SYN**。

改成**公网 IP** `203.0.113.9` 后：**立刻发起 TCP SYN，端口 8188**。

> 这是**防 DNS 重绑定（DNS rebinding）**的典型实现：
> 固件检查解析结果是否为公网地址，私有/保留地址一律拒绝连接。
> **做这类实验必须伪造一个公网 IP**，否则会误判成"固件不连接云端"。

### 1.3 为什么必须自己实现 TCP

公网 IP 不在本子网 → 插座把 SYN 交给"网关"（已被 ARP 欺骗）→ 包送到我们网卡。
但**操作系统不认识这个 IP，不会接管连接**（也不会回 SYN-ACK），
所以必须在**用户态自己实现 TCP**：收 SYN → 回 SYN-ACK → 收 ACK/数据 → 回 ACK。

TLS 用 `ssl.MemoryBIO`：把插座发来的字节喂进内存 BIO，
把 SSL 对象吐出的字节用 scapy 发回去 —— 于是能**用自签证书完成真正的 TLS 握手**。

## 2. TLS 层实测细节

### 2.1 ClientHello（62 字节，全部内容）

```
16 03 02 00 39   record: handshake, TLS1.1(0x0302), len=57
01 00 00 35      ClientHello, len=53
03 02            legacy_version = TLS 1.1
<32 字节 random>
00               session_id 长度 0
00 0e            密码套件长度 14 → 7 个
   00 35   TLS_RSA_WITH_AES_256_CBC_SHA
   00 2f   TLS_RSA_WITH_AES_128_CBC_SHA
   00 b7   TLS_RSA_WITH_AES_128_CBC_SHA256
   00 95   TLS_RSA_WITH_AES_256_CBC_SHA256
   00 b6   TLS_RSA_WITH_AES_128_CBC_SHA256
   00 94   TLS_RSA_WITH_AES_128_CBC_SHA256
   ff 01   TLS_EMPTY_RENEGOTIATION_INFO_SCSV
01 00            压缩方法：null
```
**没有 extensions 段** —— 无 SNI、无 supported_versions、无 signature_algorithms。
是一个非常精简的老 TLS 栈（ESP8266 mbedTLS 的裁剪配置）。

### 2.2 握手过程
```
插座 → ClientHello
我们 → ServerHello + Certificate + ServerHelloDone      （1109 字节）
插座 → ClientKeyExchange（RSA 加密的 premaster，256 字节）
插座 → ChangeCipherSpec + Finished
我们 → ChangeCipherSpec + Finished
✅ 握手成功 —— **插座接受了我们的自签证书**
```

### 2.3 服务端配置要点（否则会失败）
新版 OpenSSL 默认禁用 TLS 1.0/1.1 → 直接报 `UNSUPPORTED_PROTOCOL`。必须：

```python
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.minimum_version = ssl.TLSVersion.TLSv1
ctx.maximum_version = ssl.TLSVersion.TLSv1_1
ctx.set_ciphers("ALL:@SECLEVEL=0")
ctx.load_cert_chain("server.crt", "server.key")   # 必须 RSA 证书，不能用 EC
```

## 3. MQTT 层实测

### 3.1 CONNECT（插座 → 云端）

```
10 86 01                 MQTT CONNECT, 长度 134
00 04 4D 51 54 54        protocol name "MQTT"
04                       protocol level 4（MQTT 3.1.1）
c2                       connect flags：username + password + cleanSession
00 3c                    keepalive = 60s
00 10 363537353239373131343233323130   clientId(16) = "6587529711423210"
00 06 333831373835                      username(6)  = "381785"
00 60 67d1b7b7...493b                   password(96) = 48 字节 hex 串
```

| 字段 | 值 |
|---|---|
| clientId | `6587529711423210` |
| username | `381785` |
| password | `67d1b7b7cf2b55cc7c24b1883247bc0cba344552af5dd6c2848c78a3e600b65d1f0c6ace8ddcacfca7c0cde4f21e493b` |
| cleanSession | true |
| keepalive | 60s |
| MQTT 版本 | 3.1.1 (4) |

### 3.2 PUBLISH（插座 → 云端）

**`baseInfo`** —— 连上后立刻发一次：
```json
{"messageId":14515,"senderId":"6587529711423210",
 "ssid":"PDCN_IOT","mac":"B4E62D3A6E7C","sn":"B4E62D3A6E7C",
 "version":"2018041305","firmwareType":"B","mcuVersion":"2017101910",
 "protocolVersion":"1.0.0", ...}
```

**`snapshot`** —— 之后**每 60 秒**上报一次（实测 00:20:16 / 00:21:16 / 00:22:16 / 00:23:16 整分钟）：
```json
{"messageId":14630,"senderId":"6587529711423210","receiveId":"",
 "rssi":92,"snapshot":{"switch":0,"repower":"0"},
 "protocolVersion":"1.0.0"}
```
- `snapshot.switch` = 开关状态（0/1）
- `snapshot.repower` = 断电记忆设置
- `rssi` = WiFi 信号强度
- 心跳态下 `receiveId` 为**空串**（不是发给谁的回包，是主动上报）

### 3.3 主题

设备**只用三个主题**，且都是单词、无设备路径段：

| 主题 | 方向 | 说明 |
|---|---|---|
| `baseInfo` | 设备 → 云 | 上线信息（连上后立刻一次） |
| `snapshot` | 设备 → 云 | 状态上报（每 60s + 被控制时立即） |
| **`control`** | **云 → 设备** | **控制指令（★ 已实测生效）** |

**★ 反直觉的一点：插座从不发 SUBSCRIBE。**

抓到的全部应用层报文只有 `CONNECT` + 5×`PUBLISH`，**没有一条 SUBSCRIBE**。
这说明这套"MQTT"**只借用了 MQTT 的报文框架做点对点传输**：

- 设备把 broker 当成一条"上游管道"，只写不读订阅；
- 服务端要控制设备时，**直接往这条已建立的 TLS 连接里写 PUBLISH** 即可，
  不需要任何订阅关系。

> 所以自建 broker 不需要实现完整的订阅树 —— 只要维护
> `clientId → 连接` 的映射，收到带 `receiveId` 的报文时投递给对应连接就行。
> 官方 App 侧文档说的"**路由靠 payload 的 `receiveId`，不靠主题**"，在固件侧同样成立。

## 4. ★★★ 控制指令实测：已验证可完整接管

> 2026-10-02 00:24 实机验证。这一步把"**能冒充**"变成了"**能控制**"。

### 4.1 控制报文格式

往**同一条 TLS 连接**里写一个 PUBLISH，topic = `control`：

```json
{"messageId":5596385,
 "protocolVersion":"1.0.0",
 "receiveId":"6587529711423210",
 "senderId":"f9ee07acc3412b0f538d778ab05e5e80",
 "command":{"switch":1}}
```

| 字段 | 值 | 说明 |
|---|---|---|
| `receiveId` | `6587529711423210` | **目标设备 ID** = 插座自己的 clientId |
| `senderId` | `f9ee07acc3412b0f538d778ab05e5e80` | 发送方（App）的 clientId —— 见 [§4.3](#43-意外收获插座把-app-的-clientid-记在了-baseinfo-里) |
| `command` | `{"switch":1}` | **键名是 `switch`**，不是 App 侧的 `{"1":1}` ★ |
| `messageId` | 任意 | 设备会**原样回显**，用来配对请求与应答 |

### 4.2 实测往返（原样日志）

```
[00:24:02] ▶▶▶ 【下发控制】topic=control
           {"messageId":5596385,"protocolVersion":"1.0.0",
            "receiveId":"6587529711423210",
            "senderId":"f9ee07acc3412b0f538d778ab05e5e80",
            "command":{"switch":1}}
[00:24:02]   → 已发出（TLS 213 字节）
[00:24:02]   ← 明文 185 字节：
            PUBLISH topic=snapshot
            {"messageId":5596385,            ← 与请求相同 ⇒ 这是应答
             "senderId":"6587529711423210",
             "receiveId":"f9ee07acc3412b0f538d778ab05e5e80",  ← 回给"我们"
             "rssi":92,
             "snapshot":{"switch":1,"repower":"0"}}          ← 状态真的翻转了
```

**三个可验证信号，全部对上：**

1. `messageId` **原样回显** → 设备确实在处理我们的请求，而不是碰巧上报；
2. `receiveId` = **我们冒充的 App clientId** → 它按路由规则回给了"我们"；
3. `snapshot.switch` 由 `0` → `1`，且**跨两轮心跳保持**（00:24:16、00:25:16 均为 1）。

再下发 `switch=0`（00:25:33），同样立即回执 `{"switch":0}` —— **双向闭环成立**。

### 4.3 意外收获：插座把 App 的 clientId 记在了 baseInfo 里

`fake-cloud.log` 里 `app[:200]` 截断了 payload，关键字段没显示出来。
把 `fake-cloud.jsonl` 的完整 hex 解出来后（工具：`tools/mqtt-decode.py`），
`baseInfo` 尾部还有两个此前没记录的字段：

```json
{"messageId":14515, "senderId":"6587529711423210",
 "ssid":"PDCN_IOT", "mac":"B4E62D3A6E7C", "sn":"B4E62D3A6E7C",
 "version":"2018041305", "firmwareType":"B", "mcuVersion":"2017101910",
 "protocolVersion":"1.0.0",
 "reboot_count":88, "connect_count":0, "select_errno":0,
 "clientId":"f9ee07acc3412b0f538d778ab05e5e80",   ← ★ 配网时下发的 App clientId
 "checkCode":"365479"}                            ← ★ 配网校验码
```

> **教训**：日志里对 payload 做 `payload[:200]!r` 截断，会**悄悄吃掉关键字段**。
> 结构化样本必须存**完整字节**并逐条落盘 —— 这也是 `fake-cloud.py` 改成
> 实时 flush JSONL 的原因（此前进程被 kill 会丢整份样本）。

### 4.4 复现命令

```bash
# 常驻假云端 + 运行时命令注入
python tools/fake-cloud.py --target 192.168.1.23 --seconds 1800 --cmd-file control.cmd

# 另开一个终端，追加一行就立刻下发
echo "switch=1" >> control.cmd     # 开
echo "switch=0" >> control.cmd     # 关
echo "toggle"   >> control.cmd     # 按当前状态取反
```

也可以开局就排定定时控制：

```bash
python tools/fake-cloud.py --target 192.168.1.23 \
    --control "8:switch=1" --control "70:switch=0"
```

## 5. ★ 与 APK 逆向文档（`02-MQTT协议.md`）的差异

| 项 | APK 逆向（App 侧） | **真机实测（固件侧）** |
|---|---|---|
| TLS 版本 | TLS 1.2 | **TLS 1.1** |
| 证书校验 | **证书固定**（只信 `assets/test.crt`） | **完全不校验** ★ |
| username | appId `27e33ff8...` | **`381785`（product_id）** |
| password | 用户登录 token | **48 字节 hex 签名** |
| clientId | 服务端下发 | **`6587529711423210`（设备自身）** |
| keepalive | 30s | **60s** |
| 上报主题 | `snapshot`/`online`/`offline`/`error` | **`baseInfo` + `snapshot`** |
| 控制主题 | `control` | **`control`（一致）** |
| snapshot 字段 | `{"1":1}`（数字键） | **`{"switch":0,"repower":"0"}`** |
| 控制字段 | `command:{"1":1}` | **`command:{"switch":1}`** ★ 键名不同 |
| 订阅方式 | App 调 SDK（服务端绑定） | **设备从不 SUBSCRIBE，服务端直接写** |

> 说明：App 与固件是**两套独立实现**，协议相似但细节不同。
> **控制插座要面对的是固件这一套**，不能照搬 App 侧结论。
> 尤其 **证书校验**：App 做了 pinning，固件**什么都没做** —— 这正是免拆机接管的突破口。

## 6. 对"自建云端替代官方"的意义

用户的原始目标已**完全达成**：**不改插座配置、不拆机**，插座已重新可控。

要长期替代官方云，只需三件事：

1. **DNS/ARP 引导**：把 `iot.ixiaocong.com` 指向你的服务器（**必须是公网 IP**，
   或至少在固件眼里是公网地址）。
   - 内网实验：`tools/fake-cloud.py` 的 ARP 欺骗 + 伪造 DNS 方式；
   - 长期方案：内网 DNS 劫持（路由器/AdGuard/Pi-hole 自定义 A 记录）+ 让该 IP
     在固件眼里仍是公网段 —— 或用一台真·公网 VPS（最干净）。
2. **MQTT broker（TLS，自签证书即可）监听 8188**：
   因为固件不校验证书，**自签证书直接可用**，不需要任何证书注入。
   注意 **TLS 必须放开到 1.1**，且要支持 **RSA 密钥交换**（不能用 ECDHE-only）。
3. **实现业务逻辑**：接受任意 clientId/username/password（固件不校验也能连），
   收 `baseInfo`/`snapshot`，向 `control` 发 `{"command":{"switch":N}}`。

**已无技术障碍 —— 且控制链路已实机验证通过。**

### 6.1 ⚠️ 已知副作用

ARP 欺骗网关会**顺带劫持插座的全部出网流量**（因为我们把网关的 MAC 抢了过来），
所以冒充期间插座会：

- **NTP 对时失败**（它每 ~1.5 分钟查一次 `us.pool.ntp.org`，被我们答成了假 IP）
- 其他任何需要外网的功能都会失效

对"控制开关"这个目标无影响，但要知道这不是"透明代理"。
若要做得干净，需要在用户态把非目标流量**转发给真网关**（改 dst MAC 后 `sendp` 出去，
回包由网关直连插座，形成非对称路由）—— 目前**未实现**，属可选优化。
